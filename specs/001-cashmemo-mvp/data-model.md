# Data Model: Cashmemo MVP

**Database**: PostgreSQL 18  
**Model count**: 24 persistent model types, including auth-support and operational metadata  
**Authority rule**: Only a `MoneyMemo` row is authoritative financial truth. No draft, transcript, provider output, job, export, or audit row can be interpreted as a confirmed memo.

## Global Conventions

- Domain/application IDs are UUIDv7 generated by the server unless a contract explicitly accepts a caller idempotency key. Better Auth core user/session/account/verification IDs follow its pinned native PostgreSQL UUID mode and use database `gen_random_uuid()` defaults. Immutable IDs break deterministic ties.
- All content rows use `created_at TIMESTAMPTZ`; mutable rows use `updated_at TIMESTAMPTZ` and `revision BIGINT CHECK (revision > 0)`.
- All account-owned tables carry `user_id UUID NOT NULL`, even where a join could derive it. Foreign keys include ownership where possible, and `FORCE ROW LEVEL SECURITY` compares `user_id` with the transaction-local authenticated principal.
- The runtime database role is not an owner, superuser, or `BYPASSRLS` role. Maintenance/purge roles are separate, narrowly scoped, and never used by HTTP handlers.
- User strings are stored byte-equivalent to accepted input where the spec requires it. Separate normalized keys support uniqueness/search; normalized detector material is never persisted.
- User financial or capture content never appears in generic JSON operational columns. Operational JSON permits only schema-validated content-free codes.
- Hard deletes are used after lifecycle recovery windows. Soft-delete flags do not substitute for purge.

## Exact Value Objects

### Money

```text
MoneyAmount {
  amount: canonical decimal string       # API/export only, e.g. "85000" or "12.34"
  amountMinor: signed-64-safe digit string# API/export and DB conversion, e.g. "85000"
  currency: /^[A-Z]{3}$/
  currencyExponent: integer 0..3          # registry-controlled, not caller-authoritative
  currencyRegistryVersion: nonempty string
}
```

Rules:

1. Magnitude must be positive; direction is `income|expense`.
2. Input grammar is `^(0|[1-9][0-9]*)(\.[0-9]+)?$`; no sign, exponent notation, separators, whitespace, `NaN`, or `Infinity`.
3. Fractional digits cannot exceed the enabled registry exponent. Canonical response pads to the registry exponent only when the product display/export rule calls for it; stored minor units remain authoritative.
4. Significant decimal digits are at most 15. Scaled minor units must be ≤9,223,372,036,854,775,807.
5. Currency code, exponent, and registry version are snapshot fields on a memo. Registry changes never reinterpret old minor units.

### Occurrence

```text
Occurrence {
  occurredAt: RFC3339 instant                 # authoritative, with Z or numeric offset
  occurredLocal: YYYY-MM-DDTHH:mm:ss[.SSS]    # no zone suffix
  occurredTimezone: canonical IANA zone
  occurredOffsetMinutes: integer -840..840
  timezoneDatabaseVersion: nonempty string
}
```

The server validates that the local/zone/offset maps to the instant. Ambiguous/nonexistent values produce a correction response, not coercion. An occurrence over five minutes in the future is invalid.

### Revision and lifecycle

- Every mutable API representation returns a decimal-string `revision` to avoid JavaScript integer ambiguity.
- Every mutation request sends `expectedRevision`; missing/stale values fail.
- State transitions use compare-and-set inside a transaction and never accept arbitrary target states.

## Persistent Models

### 1. User

Identity root managed through the Better Auth adapter.

| Field | Type | Constraints / meaning |
|---|---|---|
| `id` | UUID | PK; Better Auth native PostgreSQL `gen_random_uuid()` default |
| `name` | TEXT | Better Auth-required internal compatibility value; always `Cashmemo account`, never user input/profile/display data |
| `email` | TEXT | Better Auth-normalized lowercase, unique; never logged |
| `email_verified` | BOOLEAN | Better Auth-owned sole verification authority; default false; protected journal requires true |
| `image` | TEXT nullable | Better Auth core compatibility; unused in Feature 001 |
| `status` | enum | `pending_verification|active|deletion_grace|purging|purged|locked` |
| `created_at`, `updated_at` | TIMESTAMPTZ | server timestamps |
| `revision` | BIGINT | account state concurrency |

Better Auth owns `id`, `name`, `email`, `email_verified`, `image`, and timestamps. Cashmemo owns status/revision and never exposes `name` or `image` through product contracts. `email_verified_at` is not retained: migration 0003 converts non-null legacy values to `email_verified=true`, converts null to false, then drops the timestamp so two authorities cannot exist. Email is erased on live account purge. A purged identity is represented outside this row only by a scope-specific deletion token that cannot reveal the raw account ID.

### 3. VerificationToken

Better Auth core PostgreSQL verification storage. In Feature 001 this table stores password-reset state only; email verification uses Better Auth's signed, expiring token and creates no row.

| Field | Type | Constraints / meaning |
|---|---|---|
| `id` | UUID | PK; Better Auth native PostgreSQL `gen_random_uuid()` default |
| `identifier` | TEXT | required/indexed; Better Auth `storeIdentifier="hashed"` stores SHA-256/base64url reset identifier, never raw reset token |
| `value` | TEXT | required; Better Auth internal user UUID, not token or journal content |
| `expires_at` | TIMESTAMPTZ | required expiry |
| `created_at`, `updated_at` | TIMESTAMPTZ | Better Auth timestamps |

Better Auth atomically consumes and deletes a successful reset row; expired consumption deletes the row and fails. Replay cannot change the password again. Migration 0003 invalidates outstanding legacy rows rather than inventing reversible values from one-way legacy fields. Reset request always returns the same public response. Raw token, identifier, value, and delivery URL are excluded from logs, traces, metrics, diagnostics, and evidence.

### 4. Session

This is Better Auth's supported core database session model, not a Cashmemo reimplementation. Better Auth owns token generation, lookup, refresh, and revocation.

| Field | Type | Constraints / meaning |
|---|---|---|
| `id`, `user_id` | UUID | PK with Better Auth native PostgreSQL UUID default; owned FK |
| `token` | TEXT | Better Auth core unique bearer token; same token is used in the session cookie; default hashing is not claimed |
| `expires_at` | TIMESTAMPTZ | Better Auth inactivity expiry; configured `expiresIn=7d`, refreshed no more often than `updateAge=1h` |
| `created_at` | TIMESTAMPTZ | Better Auth core field and Cashmemo 30-day absolute-age origin |
| `updated_at` | TIMESTAMPTZ | Better Auth core refresh metadata |
| `ip_address` | TEXT nullable | Better Auth core field; IP tracking disabled in Cashmemo configuration unless a separately approved abuse-control review enables bounded use |
| `user_agent` | TEXT nullable | Better Auth core field; treated as security metadata, excluded from telemetry/export, and purged with session/account |

`expires_at` is the public `idleExpiresAt`. Middleware also computes `absoluteExpiresAt = created_at + 30 days`; at or after that instant it invokes supported Better Auth revocation and denies the request. Revocation deletes/invalidates the Better Auth session rather than preserving a parallel Cashmemo session state. Database encryption, access restriction, backup encryption, and telemetry exclusion protect the un-hashed bearer token. Recent authentication lives only in `ReauthGrant`; it does not mutate the Better Auth token.

## State Machines

### Money Memo lifecycle

```text
active ⇄ archived
   │         │
   └────┬────┘
        ↓ delete (remember prior state, purge_after = +30 days)
recently_deleted ──restore──→ prior active|archived
        │
        ├─ immediate purge request
        └─ expiry sweeper
        ↓
     purging ──hard delete──→ absent + content-free evidence
```

Invalid transitions fail `INVALID_STATE_TRANSITION`. `recently_deleted` is excluded from all normal search/report/export-confirmed views except recovery and the declared lifecycle export.

### Assisted capture

```text
editing
  ├─ typed consent → extracting
  └─ voice start → recording → audio_ready → transcribing
transcribing
  ├─ success → transcript_review
  ├─ retryable failure → failed_recoverable
  └─ terminal failure → failed_recoverable + audio delete
transcript_review → extracting
extracting
  ├─ valid/partial → draft_review
  ├─ invalid/ambiguous → correction_required
  └─ failure → failed_recoverable
draft_review|correction_required|failed_recoverable → user editing
draft_review → explicit confirm use case → memo created + capture/draft cleanup scheduled
any pre-confirm state → discard → cleanup scheduled
```

There is deliberately no transition named `confirmed` in this table. Confirmation is a separate transaction that creates `MoneyMemo`; this prevents provider state from becoming financial truth.

### Audio lifecycle

```text
receiving → ready → transcribing → deleting → deleted
    │         │          │
    ├ cancel ─┴──────────┤
    ├ failure ───────────┤
    └ expires_at sweeper ┴→ deleting → expired/deleted
```

`delete_failed` triggers immediate alert/retry and cannot be hidden by a successful capture status. At `expires_at`, the owner refuses further STT reads and prioritizes destruction.

### Export lifecycle

```text
queued → running → ready → expired → deleting → deleted
   │        │        └→ canceled → deleting
   │        └→ failed
   └→ canceled
```

Retry with the same idempotency identity returns the same job. A job object cannot be exposed until manifest integrity and ownership checks pass.

### Account deletion

```text
active → grace ──cancel before deadline──→ active
            └─ deadline/immediate authorized continuation → purging
purging → live_purged → provider_pending → complete
   └──────── failed/pending escalation (never active)
```

`complete` requires all mandatory live stores purged and every required provider stage either confirmed or explicitly classified according to the spec. Live-purge failure is never represented as complete.

## Lifecycle and Retention Matrix

| Data class | Live location | Normal terminal trigger | Removal target / maximum | Backup/provider treatment |
|---|---|---|---|---|
| Confirmed memo | PostgreSQL | 30-day expiry or immediate purge | inaccessible immediately; live hard delete ≤24h normal ops after durable `money_memo` token | pgBackRest recovery window ≤35d; exact memo token suppresses individual resurrection |
| Recoverable draft/text | PostgreSQL + account-scoped IndexedDB replica | confirm, discard, 7d inactivity expiry | server ≤24h; client cleanup retried and on next app start | server backup ≤35d; restored expired data re-purged |
| Transcript | Draft source text | confirm, discard, failure, 7d expiry | same as draft; derived unused metadata ≤24h | no separate provider storage under approved controls |
| AI candidate/metadata | Draft strict candidate fields/provider metadata | confirm, discard, unrecoverable failure, expiry | unchosen derived metadata ≤24h | provider ZDR required |
| Raw audio | memory/encrypted task-local ephemeral | transcription, cancel, failure, one-hour expiry | terminal target ≤5m; hard maximum 1h | never backed up; STT retention disabled |
| Export package | private RustFS Primary | cancel or ≤24h expiry | inaccessible at terminal state; object delete ≤24h | every version/delete marker purge included; no retention lock on content |
| Auth/session/token | PostgreSQL | expiry, revoke, reset, account purge | access denied immediately; hard delete ≤24h where applicable | restore invalidates against deletion/session state |

| Provider copy | approved provider | request completion/account purge | ZDR/no-retention or documented deletion confirmation | provider status reported separately |
| Deletion suppression token | encrypted RustFS Secondary ledger outside PostgreSQL/pgBackRest repository | verified full backup-lineage destruction after removal floor | retain at least 42d; remove only after all resurrection-capable artifacts verified absent | no raw identity/content; no TTL authority; stale/incomplete/unavailable/unverifiable proof retains and alerts |

## RLS and Ownership Policy Pattern

### Application (cashmemo_runtime)

For every account-owned table:

```text
USING (user_id = current_setting('app.current_user_id', true)::uuid)
WITH CHECK (user_id = current_setting('app.current_user_id', true)::uuid)
```

The application starts a transaction, validates the session, uses a parameterized `SET LOCAL` equivalent that cannot be injected, then calls repositories. Empty/missing/malformed context denies all. Cross-account foreign keys use `(user_id, resource_id)` composite references so a valid ID from another account cannot be attached.

### Identity (cashmemo_identity)

For Better Auth core tables (`users`, `credential_accounts`, `sessions`, `verification_tokens`):

```text
USING (true)
WITH CHECK (true)
```

The identity role has full access to these four tables because Better Auth operations (signup, login, verification, reset, session management) must work without an authenticated Cashmemo context. `app.current_user_id` is not set during pre-auth operations.

For `idempotency_records`, the identity role has a scoped policy:

```text
USING (operation = 'signup_side_effect')
WITH CHECK (operation = 'signup_side_effect')
```

This allows the identity role to check and record signup idempotency without granting general access to application idempotency records.

`cashmemo_runtime` access to `sessions`, `credential_accounts`, and `verification_tokens` is revoked. Session lifecycle must continue through Better Auth via the identity boundary.

Maintenance operations use dedicated functions/roles with explicit data-class scope and content-free audits. No HTTP controller can acquire the maintenance role.

## Search Projection

The search vector includes only accepted `MoneyMemo.note`, current `Category.name`, and current `MoneySpace.name`. It is updated transactionally when memo/label state changes. `recently_deleted` rows may retain an internal vector during recovery but all normal search queries exclude them before ranking. A purge removes vector content with the row. Search terms are bound transiently and never persisted or logged.

## Versioned Traversal

Initial history/search/recovery queries read `HistoryListState.version`, apply ownership/lifecycle/filter predicates, and fetch `limit + 1` rows ordered by `occurred_at DESC, id DESC` in one short read-consistent transaction. Page response returns that version and an opaque cursor when more rows exist.

Continuation requires the same canonical query/filter state. Server authenticates/decrypts cursor metadata, recomputes the query/filter HMAC, and compares its version to current `HistoryListState.version` before fetching. Any mismatch returns stable `RESULTS_CHANGED` with `restartRequired=true`; no partial page is returned. Ownership and current lifecycle predicates always run, so an old cursor never retrieves a purged, inaccessible, or cross-user row. Changes committed after one page either remain invisible to that short request or increment the version and invalidate the next request. No browser traversal owns a PostgreSQL snapshot.

## Aggregation Eligibility

An eligible aggregate row satisfies:

```text
user_id = authenticated user
lifecycle_state IN ('active', 'archived')
occurred_at >= UTC(reporting-zone period start)
occurred_at <  UTC(reporting-zone next-period start)
```

Then group by currency snapshot first. Within each currency:

- income = exact sum of positive magnitudes where direction `income`;
- expenses = exact sum where direction `expense`;
- net = income − expenses;
- each dimension maps null to an explicit `uncategorized`/`unspecified` bucket;
- category ranking covers expense only and ties by normalized name then immutable category ID;
- archived rows count, drafts/deleted rows do not.

No schema object stores or derives an exchange rate or cross-currency scalar.

## Restore Reconciliation

Before a restored database can receive user traffic:

1. Restore into isolated network and use only restore-role credentials.
2. Load the content-free deletion-suppression ledger covering the backup lineage/time through current time and every referenced suppression-key version.
3. For every restored User and Money Memo immutable ID, compute `HMAC-SHA-256(key_version, entity_type || ":" || id)`. Apply `account` matches first to hard-purge the whole restored graph, then `money_memo` matches to hard-purge exact individually deleted memos and their related draft/search/provider state.
4. Re-run expired draft/memo/export/account lifecycle sweepers as of current time.
5. Rotate/revoke restored sessions and one-time tokens.
6. Run RLS isolation, currency registry, deterministic aggregate, deletion non-resurrection, and export ownership checks.
7. Inventory and tag this isolated restore copy as resurrection-capable while it exists; produce content-safe drill evidence, release network only after all mandatory checks pass, and verify destruction of abandoned/drill copies before any related token cleanup.

Suppression cleanup is a separate privileged flow. It waits until `removal_not_before_at`, inventories the full pgBackRest/PostgreSQL/RustFS lineage, and proves absence or expiry/destruction of every pre-purge backup set, WAL archive, local repository, Secondary object version, manual/operator/volume copy, replica, and isolated restore copy. Deployment policy prohibits unregistered copies/replicas and requires an independent production repository failure domain. Stale, incomplete, unavailable, or unverifiable inventory, policy drift, or any capable artifact sets `blocked`, retains the token and key version, alerts, and retries. A time-based object lifecycle never marks cleanup complete.

## Model Validation Invariants

Property/integration tests must prove:

- no `MoneyMemo` has zero/negative magnitude, unsupported currency snapshot, invalid occurrence tuple, missing owner, or draft status;
- no draft/provider/audio row participates in confirmed reporting or history;
- no aggregate function crosses currency sections;
- unchanged traversal cursors keep exact keyset order, while every stale version/query binding returns `RESULTS_CHANGED` and no inaccessible row;
- every stale update writes zero content changes;
- every identical retry maps to one authoritative ID and every conflicting retry writes nothing;
- no account-owned FK can reference another owner;
- no raw audio reaches a durable store;
- every irreversible memo/account purge has a durable correctly scoped token before hard deletion, and token cleanup cannot pass with a capable or unverifiable backup artifact;
- every terminal lifecycle has a bounded cleanup job/evidence path;
- no content-free operational model accepts a free-form string or product payload.
